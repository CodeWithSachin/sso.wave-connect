**Coordination:** sso-service's `OIDC_SECRET_KEY` must equal admin-api's.
**This is a deploy-time bear-trap** — surface it as an explicit P0
acceptance criterion below, not just a doc note.

- In Kubernetes, both `Deployment` manifests reference the same `Secret`
  by name (e.g. `sso-oidc-secret-key`), mounted as the same env var on
  both pods. One source of truth.
- In Docker Compose / local dev, both services read the same `.env` file.
- Boot-time self-check: each service emits a log line on startup with
  the first 4 bytes of `SHA-256(OIDC_SECRET_KEY)`. If those four bytes
  differ between admin-api and sso-service in the same environment, a
  CI smoke test fails. Don't log the key itself.

### 2.6 JIT implementation in identity-service

```
apps/identity-service/internal/service/federated.go (new)

  ProvisionFederated:
    1. Read identity_providers by id (verify status='active')
    2. WithTenantTx (idp.tenant_id):
       - SELECT user_id FROM federated_identities
           WHERE (idp_id, external_user_id) = ($1, $2)
           FOR UPDATE                                       -- (a)
       - If row found:
           - UPDATE last_login_at, profile_data; commit
           - Mint session via SessionService.Create (outside tx is fine)
           - Return existing user_id + session
       - If no row found AND idp.jit_provisioning=true:
           - INSERT users (status=active, email_verified=true)
           - INSERT memberships with idp.default_role
           - INSERT federated_identities (idp_id, external_user_id, ...)  -- (b)
           - INSERT refresh_token_families
           - Enqueue authz_outbox tuple via new enqueueRoleTuple()
           - Commit
           - Mint session, publish NATS user_created + user_login
           - Return new user_id + session
       - Else: return ErrJITDisabled (typed 403 at sso-service)
```

**Idempotency under concurrency** — two simultaneous callbacks for the
same `(idp_id, external_user_id)` (e.g. user double-clicks "Sign in")
must not create duplicate users. The `SELECT ... FOR UPDATE` at (a)
blocks the second tx until the first commits; once the first inserts
the federated_identities row at (b), the second tx reads it and takes
the "existing user" branch. The `(idp_id, external_user_id)` unique
constraint at the DB level is the second line of defense — if the lock
is somehow skipped (different node, missed isolation level), the
constraint surfaces as `pgx.UniqueViolation` which we map to a retry
that picks up the now-existing row.

Helper to add: `enqueueRoleTuple(ctx, tx, repo, tenantID, userID, membershipID, role)` in `authz_tuple_helpers.go` — generalization of `enqueueOwnerTuple`.

## Track 6 — Production launch (Week 6, ~3 engineer-days)

### 6.1 Real KMS for `OIDC_SECRET_KEY`

Move from env-var-only to AWS KMS (or Vault dynamic secret). Wrap
`AesGcmService.onModuleInit` to fetch the key from KMS at boot.

**Rotation procedure** — leverages the existing `v1:`/`v2:`/`vN:` prefix
already built into [aes-gcm.service.ts](apps/admin-api/src/shared/crypto/aes-gcm.service.ts)
(see the `VERSION` constant). No re-encrypt-all-at-once migration; rotate
lazily on read-write:

1. Deploy with both `OIDC_SECRET_KEY_V1` (current) and `OIDC_SECRET_KEY_V2`
   (new) set in the environment. AesGcmService gains a `Map<version → key>`
   and a `currentVersion = 'v2'`.
2. `encrypt()` writes new rows with the `v2:` prefix.
3. `decrypt()` parses the prefix and picks the right key from the map,
   so both v1 and v2 rows decrypt cleanly during the transition.
4. Background job: read all `*_enc` columns whose ciphertext starts with
   `v1:`, decrypt with v1 key, encrypt with v2 key, write back. Run as
   a Nest scheduler task in admin-api; idempotent on row id.
5. Once the background job has zero v1 rows remaining (poll a counter
   query daily), remove `OIDC_SECRET_KEY_V1` from the environment +
   delete v1 entry from the key map. Service no longer accepts v1
   ciphertext.

Document this in the AesGcmService class docstring as well as here, so
the rotation surface is discoverable from the code.

## Risk register

| Risk | Mitigation |
|---|---|
| Entra SAML / OIDC quirks (e.g. NameID format weirdness, claim casing) | Test against a real Entra dev tenant in week 1 (Eng B fixtures). Don't wait until Slice 4 to discover protocol-level surprises. |
| `OIDC_SECRET_KEY` misconfiguration in staging/prod | Track 0 fail-fast (`AesGcmService.onModuleInit` throws) means a wrong env value crashes boot, not silently writes plaintext |
| SameSite cookie behavior in privacy-mode browsers | RelayState lives in Redis, not cookies. ACS doesn't need an inbound cookie. Tested in week 4. |
| `idp_hint` confusion attack | Three-layer defense (Slice 3.3); per-IP rate limit on interstitial |
| Plaintext OIDC secrets in production (pre-Milestone B) | Track 0.4 audit query; if non-empty, write the re-encrypt migration before Slice 2 |
| crewjam/saml CVE | Pin to known-good version, vendor the dependency tree, subscribe to GitHub security advisories |
| Docker Desktop instability on dev machines blocking integration tests | Pre-compile Go binaries; document Redis + Postgres health checks in OPERATIONS.md |
| Miles team availability for dogfood | Schedule the dogfood week with Miles eng lead now (week 5–6); communicate the dogfood window early |
